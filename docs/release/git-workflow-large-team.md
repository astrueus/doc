# Git 分支、版本与协作约定（大团队参考）

> **状态：** 📖 参考稿（2026-08-17），描述 **十几人以上、多角色、要同时维护多条在线版本** 时怎么做。  
> **不是** 本仓库当前要执行的流程。现行小团队约定见 [git-workflow.md](./git-workflow.md)。  
> 两份章节大致对齐，便于对照「人少时省略了什么、人多时必须补上什么」。

大团队并不是把小团队流程「加严十倍」就完事，而是多了这些硬约束：

- 多人并行改同一模块，必须靠 **保护分支 + 强制评审 + CI**，不能靠自觉。
- 线上可能同时跑 `2.2` 和 `2.3`，必须有 **维护线（release 分支）** 和明确的 backport。
- 发版不能绑在某个人笔记本上，必须 **CI 出包、环境晋升、可回滚**。
- 破坏性变更要 **提前 RFC**，不能发版当天才写进 CHANGELOG。

## 一、适用规模与目标

| 信号 | 更像小团队（用 [git-workflow.md](./git-workflow.md)） | 更像大团队（用本文） |
|------|------------------------------------------------------|----------------------|
| 写代码人数 | 大约 2～8 | 大约 10+，或跨组 |
| 谁能发版 | 1～2 个维护者本机脚本 | 发版窗口、值班、CI 机器人 |
| 在线版本 | 基本只养一条生产 | 要同时补 2.2 和推 2.3 |
| 失败代价 | 改包重发、跟同事说一声 | 回滚、公告、审计、可能多环境 |
| 评审 | 有人看过就行 | 模块 Owner 强制通过 + CI 绿 |

**目标：** 任意一个维护者休假时，别人仍能按同一套发版、热修、回滚；`master`/`main` 不会被未评审代码冲垮。

## 二、原则（大团队版）

小团队那 7 条仍然成立，并加上：

1. **默认分支永远可构建、可部署到预发**；「能进默认分支」≠「已上生产」，生产只吃 **tag + 晋升过的制品**。
2. **禁止个人本机作为唯一发版源。** 制品在 CI 构建，checksum 入库。
3. **默认分支与 tag 受保护**：不能 force push；tag 仅发版角色可创建。
4. **代码按目录设 Owner**（CODEOWNERS）：改 `internal/mcp/` 必须 MCP 负责人过。
5. **破坏性变更先 RFC 再合代码**（至少提前一个发版周期）。
6. **每条仍在维护的 minor 线有对应 `release/X.Y`**，hotfix 必须能 backport。
7. **生产变更可追溯**：谁合的、哪次 tag、哪次部署、如何回滚，日志留在 Release / 部署系统里。

版本号只出现在 tag / 包名 / CHANGELOG，**禁止** `v2.3.0` 当长期开发分支——这条与小团队完全相同，人越多越不能破。

## 三、组织角色

| 角色 | 职责 | 典型权限 |
|------|------|----------|
| 贡献者 | 功能分支、开 PR | 推 `feat/*`，不能推默认分支 / tag |
| 模块 Owner | 评审本目录变更、接口兼容 | CODEOWNERS；可要求改设计 |
| 维护者（core） | 合入策略、依赖升级、仓库设置 | 保护规则、合紧急 PR |
| 发版官（Release Captain，可轮值） | 冻结窗口、打 tag、写发版说明、盯晋升 | 创建 tag、触发 release workflow |
| 值班 / 事故指挥官 | 热修、回滚决策 | 部署系统生产权限（与 Git 写权限分开更好） |
| 安全 / 合规（若有） | 密钥、依赖漏洞、审计 | 只读仓库 + 扫描结果 |

人数多时 **发版官与日常合 PR 的人分开**：避免「谁都能打 tag」。  
Gitea/GitHub：默认分支、`release/*`、`v*` tag 的推送限制在发版角色或机器人。

## 四、两种主干模型（先选一个）

大团队不要混用两套模型。立项时选一个写进仓库。

### 4.1 主干开发 + 短期 release 分支（推荐互联网 / 单产品）

```text
feat/* ──PR──► main（永远向前）
                 │
                 ├── 发 2.3.0：从 main 打 tag v2.3.0，制品晋升
                 └── 仍维护 2.2：release/2.2 上只合 cherry-pick，打 v2.2.x
```

- 日常全部往 `main`（或 `master`）合，靠测试和特性开关控制「未完成功能不上生产」。
- `release/X.Y` **短命或仅补丁期存在**，不是第二条开发主干。
- 适合：发版频（周 / 双周）、主要只养一条生产、能接受「未上线代码先合进 main」。

### 4.2 GitFlow 变体（推荐多版本并存、强变更控制）

```text
feat/* ──PR──► develop
                 │
                 ├── release/2.3 冻结期只修 bug ── tag v2.3.0 ──► main（只收已发布快照）
                 └── hotfix 从 main 拉，合回 main 与 develop
```

- `develop`：集成分支，允许「准备进下一版」的功能。
- `main`/`master`：**只反映已发布状态**（每个 tag 都能在 main 上找到）。
- 适合：银行 / 政企 / 要同时签合同维护 2.1 和 2.2、发版周期月级、变更委员会。

**不要**在同一仓库既要求「main 永远可发」又要求「main 只放已发布」——那是两套语义。

对本产品（文档系统、中小客户、偶发破坏性变更）：若将来变大，**优先 4.1**；若必须给客户钉死「只接受已发布提交进默认分支」，再用 4.2。

下文默认按 **4.1** 写；用 4.2 时把「合入目标」从 `main` 换成 `develop`，发版从 `release/X.Y` 打 tag 后再 merge 进 `main`。

## 五、版本号与发布列车

SemVer 规则与小团队相同（`MAJOR.MINOR.PATCH`，包名不带 `v`）。大团队额外要定 **列车（release train）**：

| 概念 | 做法 |
|------|------|
| 发版节奏 | 例如每两周一个 MINOR 或 PATCH 窗口，日期写进日历 |
| 功能进不进本班车 | 窗口前 N 天合入 `main`；错过等下一列，禁止「列车已开还强塞」 |
| 冻结 | 窗口前 1～2 天 `main` 只合 `fix/*` 与文档，发版官宣布冻结 / 解冻 |
| 多线维护 | 明确 **维护几个 minor**：例如只养当前与上一 minor（N 和 N-1），更老的只修致命漏洞或宣布 EOL |
| 预发布 | 每个正式版至少一次 `vX.Y.Z-rc.1` 上预发环境，通过再打正式 tag |

谁升 MAJOR：必须先有 RFC（第十五节），发版说明里 Breaking 置顶，给客户迁移期（例如「2.x 维护到某日」）。

内部 Round / 项目代号可以继续用，但 **对外版本只认 SemVer**，不要把 Round 5 当成客户版本号。

## 六、Tag 与制品

| 规则 | 大团队加强 |
|------|------------|
| 名字 | 仍是 `vX.Y.Z` / `vX.Y.Z-rc.N` |
| 谁创建 | 仅 CI 机器人或发版官；人肉 `git tag` 后必须立刻 `push refs/tags/...` |
| 不可变 | 保护 tag：禁止覆盖；打错发 `vX.Y.Z+1` 或 `vX.Y.Z-hotfix.1`（团队事先约定一种） |
| 签名 | 有条件则 **签名 tag**（GPG / SSH signing），CI 校验 |
| 对准的 commit | CI 构建那次 SHA，写入 Release 与包内 `version` 文件 |
| 制品 | CI 产出 zip/tar.gz，算 SHA256，挂在 Release；部署系统只拉这批文件 |

推送永远：

```bash
git push origin refs/tags/v2.3.0
```

禁止 `git push origin v2.3.0`。大团队里同名分支出现的概率更高（误建、脚本、旧习惯）。

本机 `scripts/release.*` 在大团队里降级为 **开发者 dry-run 编包**，正式发版走 CI。Token 只存在 CI 密钥库，不存在每人笔记本。

## 七、分支命名

与小团队同一套前缀，**更严**：

| 类型 | 名字 | 生命周期 |
|------|------|----------|
| 默认分支 | `main`（或继续 `master`，全公司统一） | 永久 |
| 功能 | `feat/<工单号>-<短名>` 例如 `feat/DOC-1234-oauth2` | 合入即删，建议 &lt; 1 周 |
| 修复 | `fix/DOC-1234-session` | 同上 |
| 发布维护 | `release/2.2` | 该 minor  EOL 后归档 |
| 热修 | `hotfix/DOC-5678-session` | 合入即删 |
| 实验 | `exp/<短名>` | 不直接合默认分支，需另开正式 `feat` |

强制：

- 分支名带 **工单号**（Jira / 禅道 / Gitea Issue），方便审计。
- 禁止 `v2.3.0`、禁止长期 `joker` 当集成线。
- 远程超过 14 天未更新的 `feat/*`：机器人催或自动关 PR。

## 八、权限、保护规则与 CODEOWNERS

### 8.1 保护分支（Gitea / GitHub 同类能力）

对 `main`、`release/*`：

- 禁止 force push、禁止删除。
- 禁止直推，只接受 PR。
- 要求：CI 全绿；至少 N 个评审（建议 2，模块 Owner 占 1）。
- 合入者不能充当唯一评审（人极少的模块可破例，记进仓库设置说明）。
- 管理员也不应日常绕过；紧急绕过要留 issue「为何绕过、何时补评审」。

对 tag：仅 `release` 角色或 `github-actions` / Gitea Actions 机器人可推 `v*`。

### 8.2 CODEOWNERS

仓库根（或 `.gitea/`）维护所有权，例如：

```text
/internal/mcp/          @mcp-owners
/internal/auth/         @auth-owners
/scripts/release.*      @release-captains
/docs/release/          @release-captains
/deployments/           @sre-owners
```

改这些路径的 PR 自动请求对应组。没有 Owner 的目录由 core 兜底。

### 8.3 密钥扫描

- 预提交或 CI：禁止 `.env.release`、私钥、`GITEA_TOKEN=` 进库。
- 一旦误提交：视为泄漏，轮换 Token，而不是「再 commit 删掉就完了」（历史里还在）。

## 九、日常开发与集成

1. 从最新 `main` 拉 `feat/DOC-xxx-...`。
2. 每天 rebase 或 merge `main`（团队选一种；大团队常用 **merge main 进功能分支**，避免强制 rebase 造成协作混乱；若要求线性历史则全员 rebase 并允许对功能分支 force-with-lease）。
3. PR 打开后保持 CI 绿；`main` 前进时更新分支。
4. 长功能用 **特性开关** 或拆多个 PR，避免单 PR 数千行。
5. 合入后删远程分支；默认分支使用 **squash 或 merge queue**（见下一节）。

集成频率：每天至少合一次「可合的」PR，避免周五下午巨型合并。

## 十、提交、PR、评审、合并队列

### 10.1 提交说明

仍用中文 + `类型(范围):`。大团队可加工单：

```text
fix(session): 修复只存 member_id 后误跳登录

Refs: DOC-1234
```

squash 时以 PR 标题为准，要求标题同样规范。

### 10.2 PR 模板（必填）

- 做了什么 / 为什么  
- 测试怎么跑、截图或 MCP 调用例  
- 风险等级：无 / 配置 / 数据 / 对外契约  
- 是否需要 RFC、是否要 backport 到 `release/X.Y`  
- 回滚办法（特性开关关掉 / 回上一 tag）

超过约 400 行业务 diff：拆 PR 或标「为何不能拆」。

### 10.3 评审

| 风险 | 要求 |
|------|------|
| 低（文档、测试、注释） | 1 人 + CI |
| 中（普通功能） | 1 名 Owner 或 core + CI |
| 高（鉴权、MCP 契约、迁移、发版脚本） | 2 人，含 Owner + 维护者；合并前冻结相关文档 |

评审看：正确性、兼容、可观测（日志/指标）、测试、是否误改生产默认值。

### 10.4 合并队列（人多时强烈建议）

PR 通过后不立刻合，进入队列：用即将合入后的 `main` 再跑一遍 CI，再合。避免「两个绿 PR 合在一起变红」。

Gitea 若暂无 merge queue：约定「合入前点 Update branch 再等 CI」，发版官在冻结期盯着。

合入策略全公司选一种：

- **Squash**：默认，历史干净。  
- **Merge commit**：保留功能分支结构，适合强审计「分支上每步」。  
不要有的人 squash、有的人 merge，造成 `main` 无法阅读。

## 十一、CI / CD

| 触发 | 做什么 |
|------|--------|
| 每个 PR | `go test`、lint、构建（可不打正式包）、密钥扫描 |
| 合入 `main` | 全量测试、打 **快照制品**（带 git SHA，不上生产） |
| tag `v*` | 正式制品、签名、上传 Release、部署到 **预发**（不要直接生产） |
| 手动 / 审批 | 预发 → 生产（部署系统，双人审批可选） |

失败策略：CI 红禁止合入。允许的例外只有文档-only 路径过滤（仍建议跑最短检查）。

本机脚本：仅 `dry-run` 或开发者验证交叉编译；**正式 tag 由 CI 根据工作流创建**，避免两台电脑打出两套「2.3.0」。

## 十二、环境晋升与生产

```text
CI 快照  →  开发环境（自动，跟 main）
vX.Y.Z-rc →  预发 / 客户 UAT
vX.Y.Z    →  预发冒烟通过  →  生产（Spug / 编排系统）
上一 tag  →  回滚目标
```

规则：

- 生产部署参数里记下 **tag 与制品 SHA256**。
- 禁止生产拉 `main` 现场编译。
- 数据库迁移与应用版本绑定：先迁、再切流量；回滚步骤写在 RFC 或发版说明。
- 配置（`DOC_*`、`conf/app.conf`）按环境隔离；生产密钥只在部署系统。

## 十三、发版与冻结

发版日由 **发版官** 主持，清单公开（issue 或频道）：

1. 宣布冻结：`main` 只合 `fix` / 文档。  
2. CHANGELOG 从 Unreleased 收成 `## 2.3.0`，PR 合入。  
3. CI 在约定 SHA 上打 `v2.3.0-rc.1`，部署预发。  
4. 预发冒烟（登录、文档读写、MCP、升级说明里的 breaking 步骤）。  
5. 通过则打 `v2.3.0`（或 rc 再轮）；失败则修 bug 再 rc.2，**不改已推送的 rc.1 tag**。  
6. 生产晋升、观察、解冻 `main`。  
7. 若需养旧线：从该 tag 更新 `release/2.3` 指针。

发版说明：CHANGELOG + 升级步骤（清 session、环境变量）+ 回滚到哪一个 tag。

## 十四、热修与事故

1. 事故频道：指挥官、记录员、发版官。  
2. 先 **回滚到上一已知良好 tag**（若迁移不允许回滚，走向前修复）。  
3. `hotfix/DOC-xxx` 从 **生产正在跑的 tag** 对应的 `release/X.Y`（或该 tag）拉出，不要从已经超前的 `main` 直接切包。  
4. PR：加急标签、仍要 CI + 至少一名 Owner；可缩短讨论时间，不能零评审。  
5. 打 PATCH tag（`v2.2.2`），预发再生产。  
6. **同一补丁 cherry-pick 回 `main` 和仍在维护的其他 `release/*`。**  
7. 事后复盘：根因、为何漏测、是否要加 CI 门。

禁止：在生产 tag 上 force 移动；禁止值班一个人从笔记本直接 `release.bat` 打正式版（应用 CI 热修流水线）。

## 十五、破坏性变更与 RFC

以下变更合入 `main` 前要有短 RFC（可放 `docs/rfc/` 或 issue 模板）：

- HTTP / MCP 工具契约、鉴权、Session 格式  
- 环境变量改名、默认值、删除兼容层  
- 数据迁移、不可逆清理  
- 发版 / 部署拓扑

RFC 至少包含：动机、方案对比、兼容策略、迁移步骤、回滚、计划进入哪个版本列车。  
对齐你们小团队的「决策确认」，大团队把确认 **留在仓库里**，而不是只在聊天里点头。

MAJOR 版本：给 N-1 一条维护期，写 EOL 日期。

## 十六、CHANGELOG 与发布说明

- `CHANGELOG.md`：Unreleased + 每个 **已发布 SemVer** 一节（不要只按 Round 分，对外看不懂）。  
- 自动化：可用 PR 标签（`breaking` / `feat` / `fix`）生成草稿，发版官润色。  
- Breaking 永远置顶，步骤可执行（停服 → 清 session → 部署）。  
- Release 附件与 CHANGELOG 版本号一致。

内部 Round 进度继续写在 `docs/round-*`，通过「本 Round 对应即将发布的 2.3.x」交叉引用即可。

## 十七、密钥、合规、审计

| 项 | 做法 |
|------|------|
| Token | CI 密钥库；轮换；离职关闭账号 |
| 审计 | 谁推了 tag、谁合了 PR、谁点了生产部署，能查 180 天以上 |
| 依赖 | CI 扫漏洞；高危阻塞发版或记风险接受 |
| 许可证 | 依赖许可证扫描（若有法务要求） |
| 备份 | Git 镜像；Release 制品另存 |

## 十八、上游与多仓库

MinDoc 上游仍建议 **cherry-pick + PR**，不要 merge 整库。大团队加：

- 上游跟进有 Owner，定期（例如每双周）出「跟进 / 放弃」表（可继续用 [upstream-mindoc-checklist.md](../upstream-mindoc-checklist.md)）。  
- 行为变化走 RFC。  
- 若拆成多个仓库（前端 / 后端 / 部署）：版本要么 **统一列车同号**，要么在文档里写清兼容矩阵（`doc 2.3` 需要网关 ≥ x）。本仓库目前单体，先不必拆。

## 十九、明确不要做的

- 用 `vX.Y.Z` 当开发分支。  
- 每人本机打正式 tag、非正式 CI 制品上生产。  
- 无 Owner 评审就合鉴权 / MCP / 迁移。  
- 混用 GitFlow 与「main 随时发」两套话术。  
- 冻结期强塞大功能。  
- force push `main` / `release/*` / 已发布 tag。  
- 生产 `git pull && go build`。  
- 热修只打在 `main` 却忘了 backport 到仍在跑的 `release/2.2`。  
- 聊天里口头同意 Breaking，仓库无记录。

## 二十、和小团队草案对照

| 主题 | [git-workflow.md](./git-workflow.md)（小团队） | 本文（大团队） |
|------|-----------------------------------------------|----------------|
| 主干 | `master` + 短 `feat/*` | 先选 4.1 或 4.2；常有 `release/X.Y` |
| 发版 | 维护者本机 `scripts/release.*` | CI 打 tag 与制品；本机仅 dry-run |
| 评审 | 1 人即可，可自审 | CODEOWNERS + 常要 2 人；高风险强制 |
| CI | 可口头保证 | PR 门禁；建议 merge queue |
| 环境 | 开发 / 生产，预发建议有 | 开发 → 预发 → 生产，晋升审批 |
| Breaking | 决策确认、CHANGELOG 警告 | RFC + 列车 + EOL |
| 热修 | 从 master 拉 hotfix | 从生产对应 `release/X.Y` 拉，再 backport |
| 工单号 | 不强制 | 分支名、提交、PR 建议必带 |
| 发版官 | 维护者兼任 | 轮值，与日常开发分开 |
| 同名分支/tag | 改脚本 `refs/tags/` | 同样禁止；再加保护 tag |

小团队 **不必** 为了「看起来专业」上 CODEOWNERS、merge queue、双周列车。那些是协作人数和在线版本变多之后的成本。

## 二十一、若本仓库将来变大，建议的升级路径

按需叠加，不要一次上齐：

1. **已经该做（与规模无关）：** tag 用 `refs/tags/v*` 推送；不要 `v*` 开发分支。（见小团队文档 §十七）  
2. **到 ~10 人：** `main` 保护 + 强制 1 评审 + PR 模板 + CI 测试门禁。  
3. **开始并行养两个 minor：** 引入 `release/X.Y` + backport 清单。  
4. **发版不再绑笔记本：** Gitea Actions 在 tag 上出包（现有 [release-gitea-actions.md](./release-gitea-actions.md) 往「唯一正式路径」收）。  
5. **模块边界清晰后：** CODEOWNERS（mcp / auth / 部署脚本）。  
6. **合入冲突变多：** merge queue 或「合入前必须 update + CI」。  
7. **破坏性变更变多：** `docs/rfc/` + 发版列车日历。
